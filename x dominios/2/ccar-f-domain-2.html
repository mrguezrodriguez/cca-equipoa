Domain 2
Diseño de tools e integración MCP

La descripción de una tool no es metadato: es el mecanismo con el que el modelo elige. Y cuando la selección falla, el examen quiere que cuentes las tools antes de decidir el remedio.

18% del examen 5 task statements ~11 de 60 preguntas Escenarios 1, 3 y 4
Task Statement 2.1

Diseño de la interfaz de tools

Las descripciones de las tools son el mecanismo primario con el que un LLM selecciona. No son metadato de apoyo ni documentación para humanos. Cuando el modelo recibe un conjunto de tools, lee las descripciones para decidir cuál llamar. Si dicen «Recupera información del cliente», no tiene con qué distinguir entre dos tools que se solapan.

Los cinco elementos de una descripción de producción

  1. Qué hace — su propósito, sin ambigüedad.
  2. Qué inputs espera — tipos, formatos, restricciones, campos obligatorios y opcionales.
  3. Consultas de ejemplo que maneja bien — casos concretos que anclan la comprensión del modelo.
  4. Casos límite y limitaciones — qué NO hace y qué pasa fuera del rango esperado.
  5. Fronteras explícitas — cuándo usar esta tool y no las parecidas.
MÍNIMA (provoca misrouting)
get_customer:  "Recupera información del cliente"
lookup_order:  "Recupera detalles del pedido"

DE PRODUCCIÓN (selección fiable)
get_customer:  "Busca una cuenta de cliente por email, teléfono
                o customer ID. Devuelve perfil (nombre, contacto,
                estado de cuenta, nivel de fidelidad).
                Úsala para verificar quién es el cliente.
                NO la uses para consultas sobre pedidos:
                para eso, lookup_order."

La segunda versión le da al modelo desambiguación explícita: qué identificadores acepta cada una, qué devuelve y —lo importante— cuándo no usarla.

Key concept

Cuando el misrouting viene de descripciones flojas, mejorarlas es el primer arreglo. No few-shot examples, no clasificador de enrutado, no consolidar tools. El examen premia sistemáticamente lo de poco esfuerzo y mucha palanca: mejores descripciones antes que clasificadores, acceso acotado antes que acceso total, servidores de la comunidad antes que builds propios.

Por qué esto es así

El modelo no ejecuta un algoritmo de matching: lee lenguaje natural y razona. Un few-shot example enseña tres casos concretos y añade tokens; una descripción con fronteras enseña el criterio y sirve para casos que nadie enumeró. Por eso el orden importa: arreglas la causa (el modelo no sabe distinguirlas) en vez del síntoma (falló en estas tres consultas).

Dividir tools genéricas

Una tool genérica con responsabilidad amplia crea ambigüedad. analyze_document: "Analiza un documento y devuelve resultados" se divide en tres con contratos definidos: extract_data_points (extrae campos estructurados), summarize_content (resume argumentos y conclusiones) y verify_claim_against_source (comprueba si una afirmación se sostiene en el documento). Cada una hace un trabajo estrecho y bien descrito.

Renombrar por claridad

Cuando dos nombres se parecen demasiado, renombrar arregla el solape a nivel de interfaz sin tocar la implementación: analyze_content pasa a extract_web_results con una descripción específica de web, y el propósito deja de ser ambiguo.

La trampa sutil: el system prompt

Las instrucciones sensibles a keywords en el system prompt pueden crear asociaciones no intencionadas que anulan descripciones bien escritas. Si tu system prompt dice «comprueba siempre los datos del cliente antes de continuar», el modelo puede enrutar cualquier consulta que mencione al cliente hacia get_customer por muy buenas que sean las descripciones. Después de actualizar descripciones, relee el system prompt buscando conflictos.

Condición importante — lee las dos mitades

Las descripciones son el arreglo cuando el agente tiene un número manejable de tools y simplemente no distingue dos. No lo son cuando el problema es el toolkit entero: pasadas ~4-5 tools por agente la selección se degrada solo por complejidad de decisión, y reescribir 22 descripciones no toca eso. Diagnostica cuál de los dos tienes. Lo desarrolla el 2.3.

Task Statement 2.2

Respuestas de error estructuradas

Cuando una tool MCP falla, la respuesta que devuelve determina si el agente puede recuperarse con criterio o falla a ciegas. «Operation failed» no le dice nada: ni qué pasó, ni si reintentar, ni qué probar en su lugar.

El protocolo MCP incluye el flag isError justo para esto. Marcado, el modelo sabe que la ejecución falló y puede razonar sobre la recuperación en vez de tratar el texto del error como un resultado normal.

Las cuatro categorías de error

CategoríaQué esisRetryableRecuperación
TransientTimeouts, servicio caído, rate limits. La petición es válida, el sistema no está disponible.trueReintentar tal cual tras una espera.
ValidationFormato inválido, campos que faltan, valores fuera de rango. La petición está mal formada.trueCorregir el input y reintentar.
BusinessViolación de política, límite excedido. Técnicamente válida, pero choca con una regla de negocio.falseCamino alternativo, normalmente escalado.
PermissionAcceso denegado, credenciales insuficientes.falseEscalar o usar otras credenciales.
{
  "isError": true,
  "content": [{ "type": "text", "text": "Reembolso excede el límite" }],
  "errorCategory": "business",
  "isRetryable": false,
  "description": "El importe de 750 € supera el límite de 500 € de
                  reembolso automático. Requiere aprobación de un
                  manager. Escala a un agente humano con los datos."
}
Qué señaliza isRetryable en realidad

Responde a una sola pregunta: ¿existe algún camino al éxito reintentando? No promete que la misma petición funcione sin cambios. Transient y validation comparten true pero se recuperan distinto: la primera se reenvía igual, la segunda solo después de arreglar el input. Business y permission son false por el motivo espejo: ningún reintento ayuda —una regla bloquea la petición, o hace falta otro principal con acceso. Lee el flag como «¿puede funcionar un reintento?» y luego errorCategory para saber cómo.

Fallo de acceso vs. resultado vacío válido

De todo el dominio, esta es la distinción. El examen la pregunta directamente.

  • Fallo de acceso: la tool no pudo llegar a la fuente. Timeout, auth fallida, servicio caído. Los datos podrían existir, pero no se pudo comprobar. El agente tiene que decidir si reintenta.
  • Resultado vacío válido: la tool consultó correctamente y no encontró coincidencias. La query se ejecutó bien: simplemente no hay datos. El agente no debe reintentar.
Caso de uso · los tres reintentos inútiles

Una tool devuelve un array vacío tras buscar un cliente. El agente reintenta tres veces y escala a un humano. El análisis revela que la cuenta del cliente simplemente no existe.

La tool funcionó: consultó la base de datos, no encontró coincidencias y devolvió vacío correctamente. Pero como la respuesta no distingue entre «no pude llegar a la base de datos» y «llegué y no hay nada», el agente trata ambas igual. El arreglo: que un resultado vacío no se parezca en nada a un fallo — isError: false y resultCount: 0, frente a isError: true con su categoría.

Propagación de errores en sistemas multiagente

Recuperación local con propagación selectiva:

  1. Los subagentes se recuperan localmente de fallos transitorios. Si una búsqueda da timeout, el subagente reintenta antes de molestar al coordinador.
  2. Solo se propaga lo que no se puede resolver localmente.
  3. Se incluyen resultados parciales y qué se intentó: «busqué 3 de 5 fuentes; las 4 y 5 dieron timeout; aquí van los resultados de las 3 que sí».

Esto evita dos antipatrones: suprimir errores en silencio (devolver vacío como éxito) y terminar el workflow entero por un fallo único. Los dos dejan al coordinador decidiendo a ciegas.

Trampas de examen
  • Reintentar ante un resultado vacío de una consulta que fue bien.
  • Mensajes genéricos sin errorCategory, isRetryable ni descripción.
  • Tratar errores de negocio como reintentables.
  • Suprimir errores del subagente devolviendo vacío como éxito.

Task Statement 2.3

Distribución de tools y tool_choice

Sobrecarga de tools

Dar 18 tools a un solo agente degrada la fiabilidad de selección. Cada tool añade complejidad de decisión y la tasa de error sube con el tamaño del toolkit. El rango óptimo es 4-5 tools por agente, acotadas a su rol.

Y la cantidad no es todo: la relevancia pesa igual. Un agente de síntesis no debe tener tools de búsqueda web. Dale tools fuera de su especialización y tenderá a usarlas mal: un agente de síntesis con web_search se pondrá a buscar por su cuenta en vez de usar los resultados que ya le pasaron, duplicando trabajo y gastando contexto.

Consolidar tools casi duplicadas

Dividir por rol es la respuesta obvia a la sobrecarga. Y es la equivocada cuando todas las tools hacen el mismo tipo de trabajo.

Un servidor de datos con 22 tools: tres de consulta (una por fuente) y 19 de transformación —pivot_table, calculate_percentile, normalise_currency…—. Divídelo por rol y le entregas 19 tools a un agente de transformación: el problema original, un nivel más abajo. Esas 19 colapsan en una sola porque comparten forma (datos dentro, una operación, datos fuera):

{
  "name": "transform_data",
  "description": "Aplica una transformación a un dataset.
                  Usa transform_type para elegir la operación.",
  "input_schema": {
    "properties": {
      "dataset":        { "type": "string" },
      "transform_type": { "type": "string",
                          "enum": ["pivot", "percentile",
                                   "normalise_currency", "..."] },
      "options":        { "type": "object" }
    }
  }
}

Veintidós tools se convierten en cuatro sin perder nada: cada transformación sigue siendo alcanzable, ahora como valor de enum dentro de una llamada en vez de una tool que hay que encontrar entre diecinueve descripciones casi idénticas. La precisión mejora porque la decisión difícil se hizo pequeña, no porque la capacidad se redujera.

Las tools son…El arreglo
Pocas y manejables, pero dos se parecenAfinar las descripciones (2.1)
Trabajos distintos (consultar, transformar, exportar)Dividir por rol, 4-5 cada uno
Variaciones de un mismo trabajo, con forma comúnConsolidar en una tool parametrizada
Capaces de más de lo que el agente debería poder hacerConstreñirlas
La tensión que le encanta al examen

Consolidar reduce entre cuántas tools elige el agente. Constreñir reduce hasta dónde llega cada tool. Colapsar 19 transformaciones en transform_data no le da poderes nuevos, así que no rompe el principio de mínimo privilegio. Sustituir fetch_url por load_document hace el trabajo contrario. Las dos pueden ser correctas en el mismo sistema.

Un arreglo que no es arreglo

Mover tools a un segundo servidor MCP. Las fronteras entre servidores son invisibles para el modelo: el cliente le entrega todas las tools de todos los servidores conectados como una lista plana. Un problema de 22 tools repartido en dos servidores sigue siendo un problema de 22 tools.

tool_choice: tres ajustes, tres trabajos

ValorQué obligaCuándo
"auto" (por defecto)El modelo decide si llama a una tool o devuelve texto.Operación general, cuando responder conversacionalmente es válido.
"any"DEBE llamar a una tool, pero elige cuál.Salida estructurada garantizada cuando hay varios esquemas y no sabes el tipo de documento.
{"type":"tool","name":"..."}DEBE llamar a esa tool concreta.Imponer un primer paso obligatorio: extract_metadata antes que cualquier tool de enriquecimiento.

Tras la llamada forzada, los turnos siguientes pueden volver a "auto" para el resto de pasos.

Tools cross-rol acotadas

Caso de uso · el 85% que no merece un round trip

El agente de síntesis necesita verificar datos constantemente mientras genera el informe. El diseño ingenuo devuelve el control al coordinador, que delega en el agente de búsqueda, espera y devuelve. Eso son 2-3 saltos por petición y hasta un 40% más de latencia. El 85% de esas verificaciones son búsquedas simples de milisegundos.

El arreglo: dar al agente de síntesis una tool verify_fact acotada que resuelva las simples directamente. El 15% complejo (varias fuentes, cross-referencing, juicio real) sigue pasando por el coordinador.

Sustituir genéricas por constreñidas

En vez de fetch_url (que puede traer cualquier cosa de cualquier sitio), dale load_document, que valida que sean URLs de documento. Previene el mal uso, hace el propósito más claro y reduce efectos colaterales. Es mínimo privilegio aplicado al diseño de tools.

Cómo queda repartido

AgenteTools (4-5 cada uno)
Búsqueda websearch_web, fetch_page, extract_links, save_snippet
Análisis documentalextract_metadata, extract_data_points, summarize_content, verify_claim
Síntesiscompile_report, verify_fact (acotada), format_citation, assess_coverage

Fíjate en el coordinador: dirige el workflow sin tener ninguna tool de dominio.

Task Statement 2.4

Integración de servidores MCP

La jerarquía de scoping

.mcp.json (proyecto)~/.claude.json (usuario)
Dónde viveRaíz del repositorioDirectorio home
Control de versionesSí, se comparte por gitNo, es personal
Para quéServidores que necesita todo el equipo: Jira, GitHub, conectores internosServidores experimentales, integraciones personales, pruebas antes de proponerlas
Key concept

Todas las tools de todos los servidores configurados (de proyecto y de usuario) se descubren al conectar y están disponibles simultáneamente. No hay paso de activación manual: si un servidor está configurado y accesible, sus tools aparecen en el toolkit del agente.

Expansión de variables de entorno

{
  "mcpServers": {
    "github": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": { "GITHUB_TOKEN": "${GITHUB_TOKEN}" }
    }
  }
}

La sintaxis ${VARIABLE} es lo que te permite compartir la configuración sin compartir las credenciales. Cada persona pone sus tokens en local; el fichero referencia nombres de variable, no valores. Resultado: el fichero se puede commitear sin riesgo, cada desarrollador se autentica con lo suyo, rotar un token no toca la config y no se filtra nada por el historial del repo.

Recursos MCP

Los resources exponen catálogos de contenido sin necesidad de tool calls exploratorias: resúmenes de incidencias, jerarquías de documentación, esquemas de base de datos. Sin ellos, un agente llamaría a list_tables y luego a describe_table por cada tabla, quemando llamadas solo para orientarse. Con un resource de esquema, lo sabe de entrada.

Regla mnemotécnica: los resources enseñan qué datos hay; las tools permiten actuar sobre ellos.

Construir o usar

Usa servidores de la comunidad para integraciones estándar (Jira, GitHub, Slack, Linear, Notion): están mantenidos, probados y te ahorran desarrollo. Construye uno propio solo cuando el escenario describa explícitamente flujos específicos del equipo que los de la comunidad no cubren, lógica de negocio que debe vivir en la capa de tools, o sistemas internos propietarios sin servidor público.

La trampa de la descripción escasa

Cuando una tool MCP tiene descripción pobre, el agente prefiere las built-in (como Grep) aunque la MCP sea más capaz: simplemente tiene mejor contexto sobre las built-in, cuyas descripciones son ricas. El arreglo es escribir descripciones MCP detalladas que expliquen capacidades y salidas, y que digan explícitamente cuándo usarla en lugar de la built-in.

Task Statement 2.5

Tools integradas

Seis built-in: Read, Write, Edit, Bash, Grep y Glob. Usar la equivocada cuesta tiempo, tokens de contexto o ambos.

Grep vs Glob — en una frase

Grep encuentra lo que hay DENTRO de los ficheros. Glob encuentra ficheros por su NOMBRE.

Grep — contenidoGlob — rutas
Quién llama a processLegacyOrder()Todos los ficheros de test: **/*.test.tsx
Mensajes de error que contienen «timeout»Ficheros de configuración: **/config.*
Imports de un módulo concretoTodos los MDX de un directorio

Read, Write y Edit

Edit hace modificaciones dirigidas mediante coincidencia única de texto. Es rápido y preciso porque toca solo lo que identificas.

Cuando Edit falla porque el texto aparece varias veces, eso es un mecanismo de seguridad, no un bug: impide cambiar algo que no querías tocar. El orden documentado de recuperación:

  1. Prueba Edit con el ancla más corta que sea plausiblemente única.
  2. Si la coincidencia no es única, amplía old_string con más contexto alrededor hasta que apunte a un solo sitio, o pon replace_all: true si de verdad quieres cambiar todas las apariciones.
  3. Solo si ninguna de esas dos desambigua, cae a Read + Write.
Dos trampas seguidas

El examen penaliza usar Read + Write como opción por defecto (quema contexto), y también saltar directamente a Read + Write en cuanto Edit reporta coincidencia múltiple. Ampliar el ancla o usar replace_all es la respuesta documentada; Read + Write es el último recurso, no el paso siguiente.

Exploración incremental

Mal: leer todos los ficheros de entrada. Un codebase de 200 ficheros leído entero se traga la ventana de contexto, en su mayoría con ficheros que no tienen nada que ver con la tarea. Ningún otro error de exploración cuesta tanto.

Bien: empezar estrecho y ampliar solo cuando haga falta. Grep para localizar puntos de entrada → Read para seguir imports y trazar flujos → Grep otra vez para rastrear uso → Read solo lo que el paso anterior justifique.

Caso de uso · la función deprecada

Hay que encontrar todos los ficheros que llaman a una función deprecada y los tests que la ejercitan. La secuencia correcta es Grep, luego Glob, luego Grep otra vez:

  1. Grep por el nombre de la función: encuentra cada fichero que la referencia, incluidos los tests que la importan directamente.
  2. Glob por los tests hermanos: **/OrderProcessor.test.* pilla el test que acompaña a cada llamante por convención de nombres, aunque ese test nunca mencione la función porque la ejercita a través del módulo.
  3. Grep por nombres de wrapper: si un llamante expone la función bajo otro nombre, busca ese nombre para cazar los tests que la cubren transitivamente.

Contenido para referencias directas, rutas para tests adyacentes, contenido otra vez para cobertura indirecta. No Glob primero.

Rastrear uso a través de wrappers

Patrón común: una función se define en un módulo, se re-exporta a través de un wrapper y se consume con el nombre del wrapper. Un Grep simple del nombre original se deja fuera a todos esos consumidores. La secuencia: Grep la definición → Read el fichero que la define para ver los nombres exportados → Grep cada nombre exportado → si hay barrel file (index.ts), Grep el nombre del módulo barrel.

Chuleta de desambiguación

Si dudas entre…Quédate con esto
Descripciones vs dividir vs consolidarCuenta las tools. Pocas y parecidas → descripciones. Trabajos distintos → dividir por rol. Variaciones del mismo trabajo → consolidar con enum.

Cinco frases que valen puntos

  • Las descripciones son el mecanismo primario de selección, no metadato.
  • 4-5 tools por agente, acotadas a su rol.
  • Un vacío válido nunca debe parecerse a un fallo.
  • Los errores de negocio nunca son reintentables.
  • Las fronteras entre servidores MCP son invisibles para el modelo.
