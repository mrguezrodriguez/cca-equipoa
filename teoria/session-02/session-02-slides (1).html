03La jerarquía CLAUDE.md

NivelUbicaciónCompartido vía git
User~/.claude/CLAUDE.md❌ NO — solo para ti
Project.claude/CLAUDE.md o CLAUDE.md (root)✓ SÍ — todo el equipo
Directorysubdir/CLAUDE.md✓ SÍ — aplica a esa carpeta
El error #1 del exam: un team member "no recibe" instrucciones → casi siempre porque están en ~/.claude/ (user) en vez de .claude/ (project).

04@import para modularidad

CLAUDE.md puede referenciar archivos externos con @path:

# Project CLAUDE.md

Coding standards: @./standards/coding-style.md
Testing requirements: @./standards/testing-requirements.md
Project overview: @README.md
  • @ pegado al path, sin espacio.
  • Paths relativos se resuelven respecto al archivo que importa.
  • Profundidad máxima de anidamiento: 5.

Evita el CLAUDE.md monstruoso — cada paquete importa solo lo relevante.

05.claude/rules/ con path globs

Alternativa a un CLAUDE.md monolítico. Rules por tema, con YAML frontmatter que las activa condicionalmente:

---
paths: ["**/*.test.py", "**/test_*.py"]
---

Tests usan pytest con describe/it implícito por funciones.
Usar fixtures y data factories, no hardcodear.
No mockear la BBDD — usar una BBDD de test.

La rule se carga solo cuando Claude edita un archivo que matchea el glob → ahorra contexto.

06rules con globs vs subdir/CLAUDE.md

.claude/rules/ con paths:

Cuando la convención atraviesa varios directorios.

  • Tests dispersos por todo el repo
  • Migraciones en varias carpetas
  • Archivos por extensión

subdir/CLAUDE.md

Cuando la convención está atada a una carpeta concreta.

  • terraform/CLAUDE.md
  • infra/CLAUDE.md
  • Carpeta con reglas propias
Ejemplo capstone: rules/testing.md con paths: ["**/test_*.py"] — porque los tests están repartidos al lado de cada módulo.

07Slash commands vs Skills

Slash command (.claude/commands/foo.md): atajo invocable, prompt template, sin frontmatter especial.

Skill (.claude/skills/[name]/SKILL.md): workflow reusable con frontmatter:

FrontmatterQué hace
context: forkCorre en sub-agente aislado — output verboso no contamina la sesión
allowed-toolsRestringe qué tools puede usar (seguridad)
argument-hintPide un argumento si se invoca sin parámetros

Nota: en versiones recientes commands y skills se unifican — ambos crean /name. El formato .claude/commands/ sigue soportado.

08Project scope vs User scope

ProjectUser
Commands.claude/commands/~/.claude/commands/
Skills.claude/skills/~/.claude/skills/
Compartido vía git✓ SÍ❌ NO
Variante personal de un skill del equipo: créala en ~/.claude/skills/ con nombre distinto para no pisar a los compañeros.

09Plan mode vs Direct execution

Plan mode

El modelo solo investiga y planifica; no toca nada. Produce un plan que apruebas.

  • Cambios multi-archivo
  • Decisiones arquitectónicas
  • Varios approaches válidos
  • Migraciones de librería (45+ archivos)

Direct execution

Ejecuta directamente.

  • Fix de un solo archivo
  • Stack trace claro
  • Añadir una validación
  • Cambio bien acotado
Combinado: plan mode para investigar → apruebas → direct execution para implementar.

10El Explore subagent

Subagente especializado para explorar el codebase:

  • Aísla el output verboso de descubrimiento.
  • Devuelve solo un summary.
  • Previene el agotamiento del contexto en tareas multi-fase.
No confundir: plan mode es un modo, Explore subagent es una herramienta dentro del flujo.

11Claude Code en CI/CD

El flag -p (o --print):

claude -p "Analyze this pull request for security issues"
  • Modo no-interactivo: procesa el prompt, imprime a stdout, sale.
  • La única forma correcta de correr Claude Code en CI/CD.
  • Sin -p, el job se cuelga esperando input interactivo.

Output estructurado para CI:

claude -p "Review this PR" --output-format json --json-schema '{...}'

A23.5 — La jerarquía de técnicas

Trabajar con Claude Code es iterativo. El examen pregunta cuál técnica va primero en cada situación.

SíntomaTécnica
La prosa se interpreta distinto en cada runEjemplos input/output concretos
Transformación compleja con muchos edge casesTest-driven iteration
Dominio desconocido para tiInterview pattern
Varios problemas que interactúanBatch (un solo mensaje)
Varios problemas independientesSecuencial
Trap #1: ante interpretación inconsistente, la respuesta nunca es "reescribe la prosa con más precisión". Prosa mejor sigue siendo prosa interpretable.

A33.5 — Ejemplos concretos

2–3 pares antes/después bastan. El modelo generaliza el patrón; no hace falta enumerar todos los casos.

Input:
  getUserData(userId: string): Promise<UserData>
Expected output:
  getUserData(userId: string): Promise<Result<UserData, ApiError>>

Input:
  fetchOrders(customerId: string): Promise<Order[]>
Expected output:
  fetchOrders(customerId: string): Promise<Result<Order[], ApiError>>

El bucle: observar la inconsistencia → cambiar a ejemplos → verificar en un caso nuevo → añadir un ejemplo de edge case solo si falla ahí.

A43.5 — Tests e interview pattern

Test-driven iteration

Escribe los tests primero (happy path, edge cases, performance). Luego comparte los fallos.

FAIL: testMigrationHandlesNullValues
  Expected: null preserved
  Actual:   null replaced with ""

"Expected X, got Y" no deja margen a interpretación.

Interview pattern

Para dominios donde tú no sabes qué preguntar.

"Necesito una capa de caché.
Antes de implementar, hazme
preguntas sobre requisitos,
edge cases y restricciones."

Sale invalidación, TTL, consistencia, modos de fallo.

Trap #2: no confundirlos. Ejemplos = tú sabes la transformación, el modelo la interpreta mal. Interview = tú no sabes qué considerar.

A53.5 — Batch vs secuencial

Un solo mensaje — cuando los fixes interactúan.

Tres cambios (se afectan entre sí):
1. Error responses llevan error code
2. Logging incluye ese code
3. Los types del SDK lo reflejan

El modelo necesita ver todas las restricciones a la vez o el fix de uno rompe el otro.

Secuencial — cuando son independientes.

1º "Renombra a camelCase"
   [esperas resultado]
2º "Ahora indenta a 2 espacios"

Agrupar problemas independientes confunde qué feedback aplica a qué parte.

A6Corrección: CLAUDE.md no es una cadena de precedencia

La tabla del slide 03 sugiere jerarquía. Los docs son explícitos: los archivos se concatenan en contexto, no se sobrescriben.

  • Orden de carga = de más amplio a más específico. Eso es orden, no precedencia.
  • Si dos reglas se contradicen, Claude puede elegir cualquiera.
  • CLAUDE.md se entrega como user message, no como system prompt: sin garantía de cumplimiento estricto.
Consecuencia práctica: si una regla debe cumplirse siempre (tool bloqueado, formateador obligatorio), va en settings.json o en un hook, no en CLAUDE.md. settings.json sí tiene precedencia estricta (managed > local > project > user).

Distractores típicos: "el scope más específico gana", "user-level sobrescribe project-level". Los docs no dicen ninguna de las dos.

A7CLAUDE.local.md, /memory y /compact

CLAUDE.local.md — va junto a CLAUDE.md en cualquier nivel, se carga después, se suele gitignorar. Es el ~/.claude/CLAUDE.md pero acotado a este repo.

/memory — muestra qué archivos de memoria están cargados. Herramienta de diagnóstico.

Trap: /memory no carga configuración — la revela. La config se carga sola según su ubicación. Un distractor clásico es "el dev no ha ejecutado /memory".

Estado actual del producto: /memory lista y abre los archivos; /context reporta lo que realmente entró en la sesión. Para el examen (guía v1.0), la respuesta es /memory.

Tras /compact: el CLAUDE.md de raíz vuelve (Claude lo relee de disco). Los CLAUDE.md anidados y las rules con paths: vuelven cuando toques un archivo que matchee.

A8Corrección: @path, no @import

No existe la palabra clave @import — aunque medio internet la escriba así. La directiva es @ + path, en su propia línea:

# .claude/CLAUDE.md

Coding standards:

@./standards/naming-conventions.md
@./standards/error-handling.md
Y lo importante: los imports cargan de forma eager. Partir un CLAUDE.md de 600 líneas en seis de 100 mejora el mantenimiento, pero el contexto que ve Claude pesa exactamente lo mismo.

Para reducir contexto por sesión la herramienta es .claude/rules/ con paths: — eso sí carga condicionalmente.

A9Corrección: la forma del archivo importa

Commands y skills son hoy un sistema unificado: ambos producen /nombre. Lo que cambia es la estructura en disco.

Ruta¿Crea /deploy?
.claude/commands/deploy.md✓ archivo plano
.claude/skills/deploy/SKILL.md✓ directorio + SKILL.md (canónico)
.claude/skills/deploy.md✗ archivo suelto: no se detecta
  • Si un skill y un command comparten nombre, gana el skill.
  • Ambas rutas admiten el mismo frontmatter (el slide 07 sugiere que los commands no).
  • description no está en la lista del examen, pero es el campo que decide si Claude invoca el skill solo.

A10Matiz: allowed-tools no restringe

Respuesta de examen (guía v1.0)

allowed-tools restringe a qué tools puede acceder el skill.

Producto actual

allowed-tools pre-aprueba: esas tools corren sin pedir permiso. El resto sigue disponible.

El límite real de seguridad es disallowed-tools (o deny rules en permission settings): eso sí saca la tool del pool.

En el examen, marca la opción que dice "restringe". En el repo capstone, si quieres un skill de análisis realmente read-only, usa disallowed-tools.

A113.6 — Dónde aterriza el output estructurado

claude -p \
  --output-format json \
  --json-schema '{"type":"object","properties":{
     "findings":{"type":"array","items":{"type":"object","properties":{
       "file":{"type":"string"},"line":{"type":"integer"},
       "severity":{"type":"string"},"message":{"type":"string"}}}}}}' \
  "Review this PR for security issues"
  • --output-format json envuelve el run (resultado, session ID, coste, uso).
  • --json-schema valida la salida final contra el schema. Solo en print mode.
  • Los datos validados salen en structured_output — se extraen con jq '.structured_output', no del nivel superior.

Eso permite postear comentarios inline en el archivo y línea exactos, filtrar por severidad y trackear entre runs.

A123.6 — Aislar generación de review

La misma sesión que generó el código es peor revisándolo. Retiene el razonamiento de por qué eligió ese enfoque, y no cuestiona decisiones que ya se justificó a sí misma.

# Paso 1 — generar (sesión A)
claude -p "Implement the authentication middleware"

# Paso 2 — revisar (sesión B, sin contexto compartido)
claude -p "Review the authentication middleware for security
issues, error handling gaps, and edge cases"
Distractores a descartar: "añade instrucciones de self-review", "activa extended thinking". Ninguno elimina el sesgo de justificación previa. La respuesta es una instancia independiente.

A133.6 — Review incremental

Sin contexto de reviews anteriores, cada push analiza el PR desde cero y repite los mismos hallazgos. Los que reaparecen son los que el dev vio y decidió no tocar — y un re-scan sin memoria no sabe distinguirlos de los nuevos.

claude -p --output-format json \
  "Review this PR. Findings from the previous review:
   ${PREVIOUS_FINDINGS}

   Report ONLY:
   1. New issues not in the previous findings
   2. Previous findings still present

   Do NOT re-report findings already reviewed and dismissed."

Los comentarios duplicados erosionan la confianza: si cada push genera los mismos cinco, el equipo deja de leerlos.

A143.6 — CLAUDE.md como contexto de CI

En CI, Claude Code lee los CLAUDE.md igual que en interactivo. Es el mecanismo para darle contexto de proyecto a un run automatizado.

# .claude/CLAUDE.md — sección relevante para CI
## Testing Standards

- Usar el factory pattern de test/factories/ para datos
- Los tests de integración conectan vía test/setup/db.ts
- No testear detalles privados — testear contratos públicos
- Objetivo: 80% branch coverage en código nuevo
- Fixtures: test/fixtures/users.json, test/fixtures/orders.json
  • Sin esto, la generación de tests en CI produce boilerplate de bajo valor.
  • Incluye también los tests existentes en contexto: si no, propone escenarios ya cubiertos.

A15Batch API vs real-time en CI

El Message Batches API da 50% de ahorro, con hasta 24h de procesamiento y sin SLA de latencia.

WorkflowAPIPor qué
Pre-merge check (bloqueante)Real-timeEl dev está esperando para mergear
Informe de deuda técnica nocturnoBatchNo urgente, 50% menos coste
Auditoría semanalBatchProgramada, tolera latencia
Generación de tests nocturnaBatchSe revisa por la mañana
Sample Question 11. La trampa es "pasa los dos a batch por el ahorro". El batch tampoco soporta tool calling multi-turno dentro de una request. custom_id correlaciona request y respuesta.

A16Flags CLI que conviene reconocer

System prompt

  • --system-prompt / --system-prompt-file → reemplaza
  • --append-system-prompt[-file] → añade

Append si sigue siendo un asistente de código con reglas extra. Replace si la identidad es otra — y entonces tú te haces cargo de todo.

Print mode y límites

  • --output-format text|json|stream-json
  • --max-turns <n>, --verbose
  • --permission-mode, --allowedTools, --disallowedTools, --tools
  • -c/--continue, -r/--resume <id|nombre>
  • --bare: salta hooks, skills, MCP y CLAUDE.md

A17Drill · 5 ítems tipo examen

  1. Un dev describe una transformación en prosa y Claude la interpreta distinto cada vez. ¿Qué haces primero? → 2–3 ejemplos input/output (no: prosa más precisa)
  2. Dev B clona el repo y no recibe las convenciones que sí aplica a Dev A. → Están en ~/.claude/CLAUDE.md, muévelas a project
  3. Tests dispersos junto al código en 50+ directorios, mismas convenciones. → .claude/rules/ con paths: ["**/*.test.tsx"]
  4. El job de CI se cuelga esperando input. → -p (no existen CLAUDE_HEADLESS ni --batch)
  5. Pre-merge bloqueante + informe nocturno; el manager quiere batch para ambos. → Batch solo el nocturno

Los cinco vienen de las sample questions oficiales o de sus traps directos.

B6El workflow de CI, completo

name: claude-review
on: [pull_request]

jobs:
  review:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }        # el diff necesita historia

      - name: Recuperar findings previos
        run: echo "PREV=$(cat .claude-findings.json 2>/dev/null)" >> $GITHUB_ENV

      - name: Review                     # -p: sin él, el job se cuelga
        env: { ANTHROPIC_API_KEY: "${{ secrets.ANTHROPIC_API_KEY }}" }
        run: |
          claude -p --output-format json --json-schema "$(cat schema.json)" \
            "Review this PR. Previous findings: $PREV.
             Report only new or still-unaddressed issues." \
            | jq '.structured_output' > findings.json

      - name: Postear inline
        run: ./scripts/post-comments.sh findings.json

Forma, no copia-pega. Lo examinable: -p, el schema, jq '.structured_output', y los findings previos inyectados.

  • Computer use, visión, streaming / SSE
  • Configuraciones de AWS, GCP o Azure; embeddings y vector DBs
Si en el hands-on alguien se atasca montando un MCP server propio: no entra. Configurarlo sí, desplegarlo no.

B11Drill con opciones · 1 y 2

1. Convenciones distintas por área; los tests están junto a cada componente en 50+ carpetas y deben seguir todos las mismas reglas. ¿Enfoque más mantenible?

A) Todo en el CLAUDE.md raíz · B) rules con paths: ["**/*.test.tsx"] · C) Un CLAUDE.md por carpeta con tests · D) Un skill que los devs invoquen antes de tocar tests

Por qué D tienta: parece "automático". No lo es — requiere invocación o intent match. La pregunta pide carga automática por tipo de archivo.

2. El equipo quiere /review para todos al clonar, y un dev quiere un /brainstorm personal cuyo output verboso no ensucie la conversación.

A) Ambos en ~/.claude/commands/ y que cada uno los copie · B) Ambos en .claude/commands/, brainstorm con context: fork · C) /review en .claude/commands/; brainstorm en ~/.claude/skills/brainstorm/SKILL.md con context: fork · D) /review documentado en CLAUDE.md

Por qué B tienta: el context: fork es correcto, pero mete un skill personal en el repo del equipo.

B12Drill con opciones · 3 y 4

3. Un PR toca 14 archivos. El review de un solo pase da feedback detallado en unos archivos y superficial en otros, y marca como problema en un archivo lo que aprueba en otro.

A) Un pase por archivo + un pase de integración cross-file · B) Obligar a partir los PR en 3-4 archivos · C) Modelo con más contexto · D) Tres pases y reportar solo lo que aparezca en dos

Por qué C tienta: suena a límite técnico. No lo es: es dilución de atención, y más ventana no la arregla. D además suprimiría bugs reales detectados de forma intermitente.

4. Reestructurar un monolito en microservicios: decenas de archivos, decisiones sobre fronteras de servicio y dependencias.

A) Plan mode para explorar y diseñar antes de tocar nada · B) Direct execution incremental, que las fronteras emerjan · C) Direct execution con instrucciones exhaustivas · D) Empezar directo y pasar a plan mode si aparece complejidad

Por qué D tienta: suena pragmático. Pero la complejidad ya está enunciada, no es especulativa. Esperar sorpresas es el error.

B13Drill con opciones · 5 y 6

5. Dev A tiene a Claude Code siguiendo las convenciones de naming a la perfección. Dev B, recién incorporado, obtiene resultados inconsistentes. Mismo repo, misma rama.

A) A B le falta instalar el MCP server con las reglas · B) Las reglas están en un .claude/rules/ que su setup no soporta · C) Las convenciones viven en el ~/.claude/CLAUDE.md de A · D) B no ha ejecutado /memory para cargarlas

Por qué D tienta: /memory existe y suena a "cargar". Diagnostica, no carga.

6. Quieres un /review con el checklist del equipo, disponible para todo el que clone el repo. ¿Dónde va el archivo?

A) .claude/commands/ del repositorio · B) ~/.claude/commands/ de cada dev · C) En el CLAUDE.md raíz · D) En .claude/config.json con un array commands

Ojo: .claude/skills/review/SKILL.md también sería correcto y es la ruta canónica. Si ambas aparecen como opciones, gana la de skills; si solo aparece commands, es válida.

B14Checklist de 60 segundos por ítem

  1. Lee el calificador. "Primer paso", "más efectivo", "más mantenible" y "garantizado" apuntan a respuestas distintas del mismo escenario.
  2. Busca la causa raíz en el enunciado. Si te dan logs, la causa suele estar literalmente ahí; no culpes a un agente que hizo bien su parte.
  3. ¿Hay consecuencias reales? Dinero, identidad, cumplimiento → sube por la escalera de garantía.
  4. Descarta inventos. Flags o archivos que no existen eliminan una opción de golpe.
  5. Descarta el over-engineering. Si nadie ha probado aún prompt o configuración, un clasificador entrenado no es la respuesta.
  6. Entre dos correctas, gana la proporcionada al esfuerzo que pide la pregunta.

Dos minutos por ítem. Este checklist cabe en treinta segundos y resuelve la mayoría de los empates.
