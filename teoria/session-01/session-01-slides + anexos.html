03El agentic loop en una imagen

┌─────────────────────┐ │ user_message │ └─────────┬───────────┘ ▼ ┌─────────────────────┐ │ client.messages │ ◄────┐ │ .create() │ │ └─────────┬───────────┘ │ ▼ │ ┌─────────────────────┐ │ │ response.stop_ │ │ │ reason ? │ │ └────┬───────────┬────┘ │ "tool_use" │ │ "end_turn"│ ▼ ▼ │ ┌──────────┐ ┌─────────┐ │ │ execute │ │ extract │ │ │ tools │ │ text │ │ │ + append │ │ + return│ │ └────┬─────┘ └─────────┘ │ └────────────────────────┘

La señal de control es stop_reason — no el texto, no un cap de iteraciones.

04Quién decide el siguiente paso

El temario pide reconocer la diferencia, no implementar las dos.

Dirigido por el modelo

Le das las tools y el contexto. En cada vuelta Claude elige cuál llamar. El orden emerge en ejecución.

tools = [buscar, calcular, notificar]
# el orden lo decide el modelo

Preconfigurado

Árbol de decisión o secuencia fija. El orden lo fijaste al teclear, y no cambia pase lo que pase.

datos = buscar(q)
tipo  = clasificar(datos)
return informar(tipo)

El exam favorece lo primero: se adapta a casos que nadie mapeó y encadena tools en órdenes no previstos.

La excepción que hay que memorizar: cuando la lógica de negocio exige cumplimiento determinista — operaciones financieras, comprobaciones de seguridad, requisitos regulatorios — se impone el control programático. Ahí no quieres flexibilidad, quieres garantía.

05stop_reason — los 7 valores

ValorSignificadoAcción
"tool_use"Quiere ejecutar tools antes de continuarEjecutar, añadir resultados al historial, volver a llamar
"end_turn"Ha terminado su turnoExtraer el texto final y devolverlo
"pause_turn"Un loop de server tools llegó a su tope (10 por defecto)Reenviar la respuesta tal cual para que continúe
"max_tokens"Alcanzó tu límite de max_tokensNo es un error: está truncada. Subir el límite o continuar
"stop_sequence"Salió una de tus stop_sequencesLeer response.stop_sequence para saber cuál
"refusal"Declinó responder. Llega como HTTP 200, no como errorLeer stop_details; reintentar en otro modelo
"model_context_window_exceeded"Llenó la ventana de contextoTratar la respuesta como truncada

Los tres primeros son los que continúan o cortan el loop. El resto significa "esto se acabó, bien o mal".

06Cuáles deciden control de flujo

Con client tools solamente, el loop se decide con dos valores: tool_use sigue, end_turn para.

En cuanto entran server tools (web search, code execution), pause_turn también es control de flujo: significa "no he terminado, devuélveme esto y sigo". Si tu loop lo trata como final, cortas al modelo a media tarea.

Los otros cuatro no son decisiones, son diagnósticos. Pero tienen que sacarte del loop: si no los contemplas, el if/elif no entra por ninguna rama y sigues llamando a la API con el mismo historial.

Ojo con max_tokens: la respuesta es válida, solo está cortada. Tratarla como error es tirar trabajo ya pagado.

07Patrón canónico — pseudocódigo

def run_agent(user_message):
    messages = [{"role": "user", "content": user_message}]

    for _ in range(MAX_ITERATIONS):           # safety net only
        response = client.messages.create(
            model=MODEL, tools=TOOLS, messages=messages, max_tokens=4096
        )
        messages.append({"role": "assistant", "content": response.content})

        if response.stop_reason == "end_turn":
          return {"ok": True, "texto": extract_text(response.content)}

        if response.stop_reason == "tool_use":
            tool_results = execute_tool_blocks(response.content)
            messages.append({"role": "user", "content": tool_results})
            continue

        if response.stop_reason == "pause_turn":
            continue

        return manejar_salida_anomala(response)   # max_tokens, refusal, stop_sequence

08Los 4 anti-patterns que el exam te va a tirar

#Anti-patternPor qué falla
1Cap de iteraciones como mecanismo PRIMARIOArbitrario; falla en casos legítimos largos; enmascara bugs
2Parsear texto buscando "all done", "completed"Frágil al idioma, estilo, versión del modelo
3Terminar cuando no hay texto en la respuestaUna respuesta solo-tool_use no tiene texto y NO ha terminado
4Asumir que el assistant comparte historia automáticamenteCada llamada es stateless; tú mantienes el historial
Heurística: cualquier opción que sustituye stop_reason por una heurística inventada es trampa.

09Tool use — anatomía de una respuesta

Cuando stop_reason == "tool_use", response.content es una lista de bloques:

response.content = [
    {"type": "text", "text": "Let me look up that student..."},
    {"type": "tool_use", "id": "toolu_01ABC", "name": "get_student",
     "input": {"student_id": "STU_001"}},
]

Del bloque tool_use necesitas las tres: id para emparejar el resultado, name para saber qué función llamar, input para los argumentos.

El texto puede mentir sobre la intención: una respuesta puede decir "ya lo tengo" y venir con tool_use, o terminar en silencio con end_turn. Si hay un bloque tool_use, stop_reason es siempre "tool_use". Son mutuamente excluyentes.

10Otros bloques que aparecen sin pedirlos

TipoCuándo apareceQué hacer
thinkingExtended thinking activadoDevolverlo íntegro, incluida su key signature
server_tool_useWeb search, code executionNo construyes tú el resultado — lo ejecuta Anthropic
mcp_tool_useServidores MCP conectadosIgual que arriba
text con citationsFunción de citas activadaNada especial; explica keys inesperadas
Por eso se hace messages.append({"role": "assistant", "content": response.content}) con la lista entera. Si filtras y te quedas solo con text y tool_use, rompes la firma del bloque thinking y la API rechaza la siguiente llamada.

11El bloque tool_result completo

Para responder, construyes un mensaje del role "user" con los tool_results:

messages.append({"role": "user", "content": [
    {"type": "tool_result",
     "tool_use_id": "toolu_01ABC",     # empareja con el tool_use
     "content": "...",                 # string o lista de bloques
     "is_error": True},                # ← opcional, y la que más se olvida
]})

content también acepta una lista de bloques: text, image, document o search_result. Así le devuelves un PDF o una captura, no solo texto.

is_error es la diferencia entre un script y un agente. Si tu except corta el bucle, el modelo no se entera de que algo falló. Si le devuelves el error, decide solo: reintentar con otro argumento, probar otra tool, o explicárselo al usuario.

12Las tres reglas de orden

No son keys, pero son la causa número uno de errores 400 en el loop:

  • Los tool_result van primero en el array de content. Un bloque de texto antes = 400.
  • El mensaje con los tool_result va inmediatamente después del mensaje del assistant que los pidió. Nada en medio.
  • Un tool_result por cada tool_use. Si pidió tres tools en paralelo y devuelves dos, error.
{"role": "user", "content": [
    {"type": "text", "text": "Aquí tienes:"},        # ❌ texto antes
    {"type": "tool_result", "tool_use_id": "toolu_01"},
]}

El error literal: tool_use ids were found without tool_result blocks immediately after. Si aparece, es una de estas tres.

13Nivel respuesta, no nivel bloque

{
    "id": "msg_01234",
    "type": "message",
    "role": "assistant",
    "model": "claude-sonnet-4-6",
    "content": [ ... ],
    "stop_reason": "end_turn",
    "stop_sequence": None,   # cuál disparó, si fue el caso
    "stop_details": None,    # no-null solo cuando stop_reason == "refusal"
    "usage": {"input_tokens": 100, "output_tokens": 50},
}
usage es el que vas a querer en el capstone: mide lo que cuesta cada vuelta. Como en cada iteración reenvías el historial entero, doce vueltas no cuestan doce veces la primera — cuestan bastante más.

14Tool descriptions — la Parte B de hoy

Las descripciones son cómo el modelo sabe cuándo usar cada tool.

{
    "name": "get_student",
    "description": "Retrieves student information.",  # ← genérico, malo
    ...
}

Una buena descripción incluye: qué hace, formato de inputs con ejemplos, edge cases, y cuándo usar esta tool vs sus alternativas.

Mejorar la descripción es la respuesta canónica del exam ante misrouting entre tools similares. No few-shot, no router pre-LLM, no consolidar.
